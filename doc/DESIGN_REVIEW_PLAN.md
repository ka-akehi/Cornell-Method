# 設計・仕様見直しの進め方

このメモは、Cornell Method Notebook アプリの設計・仕様を見直すための作業手順です。次回作業では、この順番で確認し、決定事項を `AGENTS.md` に反映します。

## 目的

- 現行仕様をそのまま実装するのではなく、個人ローカル利用に必要な範囲へ整理する。
- MVP と後回しにする機能を分け、実装順序を明確にする。
- DB、API、UI、テストの責務と優先順位を揃える。
- 現行実装は古いライブラリや過去仕様を含むため、実装段階ではフルリニューアルする前提で設計する。

## 作業体制

- ユーザーは発注者として、仕様判断・優先順位・方針決定を行う。
- Manager は発注者と相談し、仕様を具体化して Worker に渡せる粒度のタスクへ分割する。
- Worker は Manager が投入した 1 タスクを実装し、変更内容と検証結果を報告する。
- Manager / Worker は、仕様が不明な場合や方針判断が必要な場合に推測で進めず、発注者へ随時質問する。
- 技術的に不整合、過剰設計、実装リスクがある場合は、作業者側から論点として提示する。

## 設計前提

- 現行実装は制約として扱わず、As-Is 把握と設計上の論点抽出にのみ使う。
- 実装段階では、依存ライブラリ、DB スキーマ、API、UI をフルリニューアルする前提とする。
- 既存コードに合わせて仕様を歪めず、発注者が使いたい Cornell Method Notebook の To-Be 設計を優先する。
- ライブラリ選定や技術方針で判断が必要な場合は、Manager が発注者へ確認してから Worker タスク化する。
- 発注者は設計初心者である前提を置き、Manager は発注者が見逃しやすい重要な分岐点、リスク、判断基準を先回りして提示する。
- 重要な分岐点では、Manager は「何を決める必要があるか」「選択肢」「各選択肢の影響」「Manager 推奨」を明示する。
- 発注者から設計学習目的で判断理由や判断基準を質問された場合は、回答内容を `learning-notes/DESIGN_LEARNING_NOTES.md` に追記する。

## Step 1: 現行仕様を棚卸しする

`AGENTS.md` の機能を、以下の単位で一覧化します。

- 画面
- DB モデル
- API
- UI 操作
- バリデーション
- バックアップ
- エクスポート
- 復習タスク
- Undo / 自動保存 / 楽観ロック
- A11y / キーボード操作
- テスト・受け入れ条件

この時点では実装可否を判断せず、まず仕様として存在するものを抜き出します。

現行コードから確認できる事実は `doc/AS_IS_DESIGN_INVENTORY.md` を参照します。ただし、現行実装は新設計の制約ではなく、移行時に捨てるもの・残す概念・見直す論点を抽出するための資料として扱います。

## Step 2: 機能を分類する

各機能を次の 4 種類に分類します。

| 分類 | 意味 |
| --- | --- |
| MVP | 最初に必ず作る機能 |
| Phase 2 | MVP 後に追加する機能 |
| 保留 | 要件として残すが、今は設計を固定しない機能 |
| 削除候補 | 個人利用には重すぎる、または価値が薄い機能 |

分類時の判断基準:

- Cornell Method Notebook として最低限必要か
- ローカル個人利用で本当に必要か
- 実装コストに対して利用頻度が高いか
- DB/API/UI の複雑さを大きく増やさないか
- 後から追加しても設計破綻しないか

## Step 3: MVP を定義する

まずは以下を MVP 候補として検討します。

- ノート一覧
- ノート作成
- ノート編集
- ノート閲覧
- Cornell レイアウト
- Markdown 入力・表示
- キーワード欄、ノート欄、サマリー欄
- 本文を隠す復習モード
- 簡単な復習予定日 / 復習済み管理
- 要約未作成表示
- タグ付け
- タイトル・日付・概要
- SQLite への保存
- 最低限の検索・絞り込み
- 最低限のバックアップ

MVP から外す候補:

- PDF 出力
- 高度な復習タスク（通知、タブ分け、間隔反復など）
- Undo スナックバー
- 詳細な楽観ロック
- 複雑なドラフト自動保存
- D&D 並び替え
- タグ管理の右クリックメニュー
- バックアップログ UI
- HTML エクスポート切替
- 高度な A11y 対応

## Step 4: DB 設計を見直す

MVP に必要な最小モデルを確認します。

検討ポイント:

- `Notebook` に持たせる情報は何か
- `CueCard` と `NoteCard` を分ける必要があるか
- `NoteCueLink` は MVP で必要か
- Draft 専用テーブルは MVP で必要か
- Review Progress は Phase 2 にできるか
- Soft Delete / Undo Buffer は MVP で必要か
- Tag は正規化するか、簡易実装から始めるか

この段階で、Prisma スキーマを直接変更する前に設計方針を文章で決めます。

## Step 5: API 設計を見直す

MVP で必要な API だけに絞ります。

候補:

- `GET /api/notes`
- `POST /api/notes`
- `GET /api/notes/:id`
- `PATCH /api/notes/:id`
- `DELETE /api/notes/:id`
- `GET /api/tags`
- `POST /api/tags`

検討ポイント:

- エラー形式は統一するか
- 一覧検索の条件はどこまで対応するか
- 保存 API は確定保存のみから始めるか
- 自動保存 API を MVP に含めるか
- 削除は物理削除かソフトデリートか

## Step 6: UI 設計を見直す

MVP の画面構成を決めます。

候補:

- `/notes`: 一覧
- `/notes/new`: 新規作成
- `/notes/[id]`: 詳細・編集

検討ポイント:

- 閲覧モードと編集モードを分けるか
- 新規作成と編集で同じフォームを使うか
- Markdown プレビューを常時表示するか
- カード追加・削除の操作をどこまで作るか
- D&D ではなく上下ボタンから始めるか
- タグ入力はどこまで高機能にするか

## Step 7: テスト観点を更新する

`doc/TEST_SCENARIOS.md` を MVP 用に整理します。

まず確認したい流れ:

- ノートを作成できる
- 作成したノートが一覧に出る
- ノートを編集して保存できる
- Markdown が表示される
- タグで絞り込める
- 日付で絞り込める
- 削除できる
- バックアップコマンドが動く

MVP から外した機能のテストは、Phase 2 セクションへ移します。

## Step 8: `AGENTS.md` に反映する

設計見直しで決めた内容を `AGENTS.md` に反映します。

反映方針:

- MVP 仕様を先に書く
- Phase 2 以降の仕様は別セクションに分ける
- 保留事項は「未決事項」として明示する
- 削除候補は必要なら履歴として短く残す
- 実装済みと未実装が混ざらないようにする

## Step 9: 実装タスクへ分割する

設計確定後、`codex-queue` に投入しやすい粒度へ分割します。

タスク例:

- `AGENTS.md` を MVP 仕様に再構成する
- Prisma スキーマを MVP 方針に合わせて整理する
- ノート CRUD API を MVP 仕様に揃える
- ノート一覧 UI を MVP 仕様に揃える
- ノート編集 UI を MVP 仕様に揃える
- テストシナリオを MVP / Phase 2 に分ける
- README にセットアップ手順を追記する

## 次回作業の開始ポイント

次回は以下から始めます。

1. `AGENTS.md` の機能を棚卸しする
2. 各機能を MVP / Phase 2 / 保留 / 削除候補に分類する
3. MVP の画面、DB、API の最小構成を決める
4. 決定事項をこのメモまたは `AGENTS.md` に反映する
