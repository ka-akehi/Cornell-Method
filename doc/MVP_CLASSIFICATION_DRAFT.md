# MVP / Phase 2 分類案

確認日: 2026-06-14

## 位置づけ

このドキュメントは、`AGENTS.md` の現行仕様と `doc/AS_IS_DESIGN_INVENTORY.md` の As-Is 棚卸しを元にした、設計見直しの分類案です。

これは決定版ではありません。発注者確認後、確定した内容を `AGENTS.md` に反映します。

## 発注者決定事項

- 現行実装は古いライブラリや過去仕様を含むため、新設計の制約として扱わない。
- 実装段階ではフルリニューアルする。
- As-Is は参考資料として使い、To-Be 設計は発注者が必要とする体験を優先して決める。
- MVP に「本文を隠す復習モード」を含める。
- MVP に「簡単な復習予定日 / 復習済み管理」を含める。
- MVP のノート本文はカード分割せず、1 つの Markdown 本文として扱う。
- キーワード / 質問は Cue リストとして扱う。
- MVP の Cue / Tag 更新は全置換とし、差分更新は必要になった場合の Phase 2 要件とする。
- MVP の Markdown 入力は `textarea + preview` とし、Markdown 専用エディタライブラリは Phase 2 要件とする。
- MVP の API は TypeScript / Next.js Route Handler で実装し、Rust API は Phase 2 検討事項とする。
- MVP はローカル SQLite で小さく作り、Vercel deploy / Supabase 移行は Phase 2 検討事項とする。
- Vercel deploy を行う場合は、無料範囲を優先し、アプリ側Basic認証相当をセットで実装する。
- Vercel deploy 時は SQLite ファイルをそのまま永続DBとして使わず、Supabase Postgres またはSQLite互換の外部DBを検討する。

## 分類基準

| 分類 | 意味 |
| --- | --- |
| MVP | 最初の完成ラインに含める |
| Phase 2 | MVP 完成後に追加する |
| 保留 | 要件として残すが、今は仕様を固定しない |
| 削除候補 | 個人ローカル利用では優先度が低い、または過剰 |

判断観点:

- Cornell Method Notebook として必須か
- 個人ローカル利用で継続的に使うか
- 後から追加しても設計破綻しないか
- DB/API/UI/テストの複雑さをどれだけ増やすか

## Phase 2 案

| 機能 | 理由 | 現行実装の扱い |
| --- | --- | --- |
| ドラフト自動保存 | 便利だが競合制御・UI状態・テストが重い | 現行実装は使わず再設計 |
| 楽観ロック | 個人利用では優先度低め。自動保存とセットなら必要 | 現行実装は使わず再設計 |
| Undo スナックバー | 削除体験として有用だが MVP 必須ではない | 現行実装は使わず再設計 |
| 高度な復習タスク | 通知、タブ分け、間隔反復などは MVP 後でよい | 現行実装は使わず再設計 |
| PDF 出力 | 便利だが Playwright 依存と検証負荷がある | ライブラリ選定から再検討 |
| Cue / Tag 差分更新 | MVP では保守性を優先して全置換する。大量データ・自動保存・履歴管理が必要になったら検討 | To-Be として再検討 |
| Markdown 専用エディタ | 入力補助、ツールバー、ショートカット、エディタ内プレビューが必要になったら検討 | ライブラリ選定から再検討 |
| Rust API サーバー | API独立化、重い処理、ローカル常駐プロセス、CLI/デスクトップ化が必要になったら検討 | To-Be として再検討 |
| Vercel deploy + Basic認証 | 無料枠で運用できる場合、アプリ側Basic認証相当で保護した上で検討 | To-Be として再検討 |
| Supabase Postgres 移行 | SQLiteではなくクラウドDBを使いたくなった場合に検討 | To-Be として再検討 |
| SQLite互換の外部DB検討 | SQLiteライクな運用をVercel上でも維持したい場合、Turso / libSQL などを比較する | To-Be として再検討 |
| Vercel生成URL / production domain 向けアクセス制御 | 個人利用でもVercelに載せるとURLが生成されるため、まずBasic認証相当で保護する | To-Be として再検討 |
| D&D 並び替え | 操作性は上がるが A11y とテスト負荷がある | 現行実装は使わず再設計 |
| 閲覧モード / 編集モード切替 | 読み返し体験として有用 | To-Be として再検討 |
| ノートカード hidden 表示制御 | 閲覧体験の拡張 | To-Be として再検討 |
| タグ管理 UI | 名称変更・削除は便利だが MVP ではなくてもよい | To-Be として再検討 |
| バックアップログ UI/DB 連携 | 運用性向上だが、個人利用では後回し可能 | 方式から再検討 |
| 起動時クリーンアップ | 長期運用では必要 | 方式から再検討 |
| A11y 強化 | 品質向上として必要 | To-Be として定義 |

## 保留案

| 機能 | 保留理由 |
| --- | --- |
| HTML エクスポート切替 | 将来の出力形式次第。現時点では PDF と競合する |
| テンプレート拡張構造 | 初期テンプレートは Cornell のみのため、先に抽象化しすぎない |
| 週次ドラフトクリーンアップバッチ | MVP でドラフト自動保存を外すなら不要になる可能性がある |
| 詳細なキーボードショートカット | Cmd/Ctrl+S 以外は利用頻度と実装コストを確認したい |
| グローバルナビの復習タスク未完バッジ | 復習タスクを Phase 2 にするなら後回し |

## 削除候補

| 機能 | 理由 |
| --- | --- |
| 右クリックメニューでのタグ管理 | 個人ローカル利用では発見性が低く、通常ボタンや管理画面の方がわかりやすい |
| 同一ノートで 10 件以上の `isDraft=true` を防ぐ仕様 | 現行 DB は 1:1 DraftState であり、仕様と構造が合っていない |
| 外部 API 連携前提の設計記述 | 現行方針は外部 API 連携なし |
| 高度な権限・認証仕様 | 個人ローカル利用で認証なしのため不要 |

## 設計方針

**フルリニューアル前提で、MVP 仕様に合わせてシンプルに再設計する。**

ドラフト、自動保存、PDF、Undo などは最初から全部入りにせず、ノート CRUD、Cornell レイアウト、タグ、検索、バックアップに加えて、コーネルメソッドの想起と復習を支える最小機能を To-Be として定義します。

メリット:

- 古いライブラリや既存実装の都合に引っ張られない。
- DB/API/UI の責務を最初から揃えられる。
- MVP のテスト観点が明確になる。
- Phase 2 機能を、必要になった時点で現在の設計に合わせて追加できる。

リスク:

- 既存コードを流用しないため、実装時の作業量は増える。
- 現行実装に含まれる機能を捨てる判断が必要になる。
- ライブラリ選定を改めて行う必要がある。
