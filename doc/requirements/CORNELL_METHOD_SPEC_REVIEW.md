# コーネルメソッド観点の仕様レビュー

確認日: 2026-06-14

## 目的

本書は、作成時点の仕様案が「コーネルメソッドを活用したノートアプリ」として妥当かをレビューした記録です。

レビュー時点ではフルリニューアルを前提とし、既存コードを評価対象に含めず、To-Be 仕様の妥当性を評価しました。

履歴注記: 本書は 2026-06-14 時点の旧仕様に対するレビュー記録です。現行のノート項目・受け入れ判断は `doc/implementation/MVP_CONTRACT.md` を正とします。

## 前提: コーネルメソッドで支援すべき流れ

コーネルメソッドは、3 分割のレイアウトを使って学習プロセスを支援するノート術です。

レビューでは、次の基本フローを支援対象としました。

1. 記録する
   - 授業、読書、動画、調査などからノート本文を書く。
2. 整理する
   - 左欄にキーワード、質問、論点、用語を抜き出す。
3. 要約する
   - 下部に自分の言葉で要点をまとめる。
4. 想起する
   - キーワード / 質問だけを見て、ノート本文を思い出す。
5. 復習する
   - 時間を置いて再確認し、理解度を更新する。

アプリの中心には、**あとで思い出す・理解を確認する・復習する**ことを置くべきです。

## 現行仕様案の良い点

| 観点 | 評価 |
| --- | --- |
| Cornell レイアウト | キーワード欄、ノート欄、サマリー欄があり、基本構造は合っている |
| Markdown | 箇条書き、チェックリスト、強調を扱えるため学習ノートと相性が良い |
| タグ | 科目、テーマ、教材、試験範囲などで整理できる |
| 日付 | 学習記録、復習タイミング、時系列確認に使える |
| 一覧検索 | 後から探して読み返す用途に必要 |
| 復習タスク | コーネルメソッドの「Review」に対応する候補になっている |

## 現行仕様案の問題点

| ID | 問題 | 影響 |
| --- | --- | --- |
| P-001 | CRUD、タグ、PDF、自動保存などのアプリ機能が先行している | コーネルメソッドの学習体験が仕様の中心から外れる |
| P-002 | 「想起する」ための仕様が弱い | 左欄を見て右欄を思い出す練習ができない |
| P-003 | サマリー欄が単なる Markdown 欄になっている | 自分の言葉で要約する行為を促せない |
| P-004 | 復習タスクが Phase 2 扱いになっている | Cornell Method の Review を MVP で支援しない設計になり得る |
| P-005 | カード単位や D&D が先に複雑化している | ノートを書く流れより UI 操作の複雑さが目立つ |
| P-006 | タグ仕様が細かすぎる | 学習体験より管理機能に設計コストが寄る |
| P-007 | PDF 出力の優先度が高く見える | 学習中の活用より成果物出力に寄る |
| P-008 | 「ノート本文」と「キーワード/質問」の厳密なカードリンクを前提としている | Cornell Note では、人間が見て思い出せる配置が重要 |

## 仕様として見直すべき中心軸

レビューでは、MVP の中心を次のように提案しました。

> コーネルメソッドの「記録、整理、要約、想起、復習」を回せるアプリにする。保存は、この学習サイクルを支える。

MVP では、学習サイクルに直接関係する機能を優先します。

## To-Be で重視する体験

### 1. 書く

- ノート本文を素早く書ける。
- 講義中、読書中、動画視聴中でも入力を邪魔しない。
- Markdown を使えるようにしつつ、記法を知らなくても入力できる UI にする。

### 2. 整理する

- 後からキーワード、質問、用語、論点を左欄に追加できる。
- 左欄は、あとで思い出すための手がかりとして扱う。本文の見出しには限定しない。
- キーワード欄とノート本文の厳密な紐付けは、MVP では必須にしない。

### 3. 要約する

- サマリー欄は目立つ位置に置く。
- 未入力の場合に「要約未作成」とわかる。
- 要約は本文とは別に保存する。

### 4. 想起する

- キーワード / 質問だけを表示し、ノート本文を一時的に隠せる。
- その状態で自分の記憶を確認できる。
- MVP では採点や理解度管理までは不要。

### 5. 復習する

- 復習対象のノートがわかる。
- MVP の復習管理は、簡単な「復習予定日」または「復習済み」に限定してよい。高度な間隔反復は対象外とする。
- 復習機能をすべて Phase 2 に送ると、コーネルメソッドらしさが弱くなる。

## 将来構想: AI クイズを入れる場合の設計論点

AI による自動復習クイズ生成は、復習モードを拡張する将来構想です。MVP と既存 Phase 2 の実装対象には含めません。

Cornell Method の基本は、左側の Cue / キーワード / 質問を見て、右側本文を思い出す想起練習です。復習タスク画面は「今日復習すべきノートへ誘導する入口」とし、AI クイズはノート詳細の復習モード内で解く想起支援機能にします。

AI クイズは次を前提に設計します。

- 復習時は左側の Cue / キーワード / 質問を表示し、右側本文を隠す。
- AI クイズは左側 Cue を出題軸・ヒントとして使い、右側本文やサマリーの理解を問う。
- 左側に見えている語句そのものが答えになる問題は極力避ける。
- 初期形式は一問一答と穴埋めを中心にする。
- 選択式は、答えが長い場合や理解確認に向く場合に限る拡張形式として検討する。誤答選択肢の品質管理と誤学習防止を設計条件に含める。
- 目的は答え合わせとし、解答後に正答、根拠、解説を表示する。採点は目的にしない。
- 一問一答 / 穴埋めでは厳密な自動採点を必須にしない。選択式を採用する場合のみ選択肢ベースの正誤判定を検討する。
- 初期の生成タイミングは、ユーザーが「クイズ生成」ボタンを押したときにする。
- 初期段階ではクイズを保存せず、オンデマンドで生成する。
- 将来保存する場合も生成を続け、クイズ候補プールを増やす。同じクイズだけを固定して再利用しない。復習時は候補プールからランダムまたは条件付きで 5〜10 問を出題する。
- 外部 API は利用しない。Rust API 実装が完了した後、Rust 側で Local LLM を扱う方針を第一候補にする。
- 初期はモデル自体を学習させない。ノート、Cue、サマリー、生成クイズ、復習結果を蓄積し、Local LLM に渡す知識ベースを育てる。十分なデータが蓄積された段階で、追加学習 / fine-tuning に挑戦する余地を残す。

MVP に含めない理由は次のとおりです。

- MVP では、「左側 Cue を見て右側本文を思い出す」復習モードの実装と検証を優先する。
- AI クイズは生成品質、誤答選択肢、根拠表示、誤学習防止、保存方針、Local LLM の性能と配布方法まで設計範囲が広い。
- 外部 API を使わない制約があるため、Rust API と Local LLM の実現方式が固まる前に実装へ入ると手戻りが大きい。

## 将来構想: AI Cue 候補提案を入れる場合の設計論点

Local LLM による Cue / キーワード / 質問の不足候補提案は、Cornell Method のノート整理を補助する将来構想です。MVP と既存 Phase 2 の実装対象には含めません。

Cornell Method では、ユーザー自身が本文から重要点を選び、左側の Cue / キーワード / 質問として整理する行為が学習体験の中心です。AI の役割は、ユーザーが Cue を書いた後に、不足していそうな候補を提案することに限定します。左側を自動入力しません。

推奨する操作の流れは次のとおりです。

- ユーザーがまず本文、サマリー、Cue / キーワード / 質問を自分で書く。
- AI は本文・サマリー・既存 Cue を見て、不足していそうな重要概念、問いに変換できる論点、重複しないキーワードを候補として出す。
- ユーザーは候補を `追加` / `編集して追加` / `無視` できる。
- 候補は自動採用しない。採用判断と最終表現はユーザーが行う。

AI クイズと Cue 候補提案は、役割を次のように分けます。

- AI クイズは、復習時に左側 Cue を出題軸・ヒントとして使う想起支援。
- AI Cue 候補提案は、ノート整理時または復習前に左側の不足を見直す整理支援。
- どちらも、Local LLM を利用でき、知識ベースに十分なデータが蓄積した後の将来拡張であり、MVP 安定化や既存 Phase 2 の優先順位を上書きしない。

## MVP を見直す場合の推奨範囲

### MVP に含めるべきもの

| 機能 | 理由 |
| --- | --- |
| ノート作成・編集・保存 | 基本 |
| Cornell レイアウト | 中核 |
| キーワード / 質問欄 | 想起の手がかり |
| ノート本文欄 | 記録の中心 |
| サマリー欄 | 要約の中心 |
| Markdown 入力・表示 | 学習ノートとして有用 |
| ノート一覧 | 読み返しの入口 |
| タイトル検索 | 最低限の検索 |
| タグ | 科目・テーマ分類 |
| 日付 | 学習日と復習の基準 |
| 本文を隠す復習モード | Cornell Method の想起を支援するため |
| 要約未作成の表示 | 要約習慣を促すため |
| 復習予定日または復習済みフラグ | Review を MVP に薄く含めるため |
| 最低限バックアップ | ローカル利用の安全性 |

### MVP から外してよいもの

| 機能 | 理由 |
| --- | --- |
| PDF 出力 | コーネルメソッドの実践には直接不要 |
| D&D 並び替え | 最初は上下移動または作成順で十分 |
| 自動保存 | 便利だが学習フローの中核ではない |
| 楽観ロック | 個人ローカル利用では優先度が低い |
| Undo スナックバー | 削除確認で代替可能 |
| 複雑なタグ管理 | 科目・テーマ分類ができれば十分 |
| カード間の厳密な多対多リンク | MVP では学習体験より実装複雑度が勝つ |
| 高度な復習アルゴリズム | まずは復習対象がわかればよい |

## DB 設計への示唆

レビューでは、MVP のデータ構造として次の候補を優先しました。

- `Notebook`
  - title
  - noteDate
  - sourceType
  - sourceTitle
  - overview
  - body
  - summary
  - reviewModeEnabled or reviewStatus
  - nextReviewDate
- `Cue`
  - notebookId
  - text
  - order
- `Tag`
  - name
- `NotebookTag`
  - notebookId
  - tagId

データ設計で残した検討事項は次のとおりです。

- ノート本文はカード分割せず、MVP では 1 つの Markdown 本文でもよい。
- キーワード / 質問は複数行または単純なリストでよい。
- Note と Cue の多対多リンクは Phase 2 でよい。

## UI 設計への示唆

レビューでは、MVP の詳細画面に次の 3 状態を提案しました。

- 編集モード
  - 右欄に本文を書く。
  - 左欄にキーワード / 質問を書く。
  - 下部にサマリーを書く。
- 閲覧モード
  - Cornell レイアウトで読む。
- 復習モード
  - 左欄とサマリーを表示。
  - ノート本文は隠す / 表示するを切り替える。

## Manager 評価

作成時点の仕様案は、コーネルメソッドの基本レイアウトを押さえていました。一方で、CRUD、タグ、PDF、自動保存の仕様が、想起と復習より先に詳しく定義されていました。その結果、想起と復習の要件が相対的に薄い状態でした。

レビューでは、MVP で **本文を隠してキーワードから想起する復習モード** を優先するよう提案しました。PDF と D&D は MVP の対象外とする提案です。
