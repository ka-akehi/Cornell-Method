# MVP UI Design Artifact Gap Review

作成日: 2026-07-08

## 目的

この文書は、Cornell Method Notebook の過去 MVP 設計時に不足していた UI 設計成果物を、事実記録として整理するレビューです。

`learning-notes/` は設計学習メモの置き場であり、過去設計時の不足点一覧やレビュー本文の主置き場ではありません。そのため、UI 設計成果物の不足に関する事実記録はこの `doc/review/` 配下へ置きます。

## 位置づけ

- 対象は MVP 設計時の UI 設計成果物の不足です。
- 現行実装の合否判定や追加実装 task の一覧ではありません。
- 学習上の判断基準は [learning-notes/ui-design/ui-implementation-readiness.md](../../learning-notes/ui-design/ui-implementation-readiness.md) を参照します。
- 実装との差分棚卸しは [MVP_DETAIL_GAP_INVENTORY.md](MVP_DETAIL_GAP_INVENTORY.md) を参照します。

## 確認できた成果物

MVP 設計時には、次の成果物は存在していました。

| 成果物 | 役割 | 備考 |
| --- | --- | --- |
| Markdown の画面設計書 | 画面、項目、操作、validation の整理 | `doc/screens/` 配下 |
| Mermaid の画面遷移図 | 画面間の導線整理 | `doc/diagrams/` 配下 |
| 状態遷移図 | 保存、削除、復習などの状態整理 | `doc/diagrams/` 配下 |
| 実装後スクリーンショット | 実装結果の確認、README 掲載、回帰確認 | `doc/assets/screenshots/` 配下 |

これらは MVP の仕様整理や実装後確認には有効でした。一方で、実装前に UI 体験を視覚的に合意するための成果物としては不足がありました。

## 不足していた UI 設計成果物

### 画面レイアウト案

実装前に、低忠実度ワイヤフレームとして次を確認する成果物が不足していました。

- ノート一覧の検索条件、タグ条件、一覧カード、主要操作の配置
- 新規作成画面の基本情報、Cue、Note、Summary、保存操作の配置
- 詳細画面の閲覧、編集、復習モードのレイアウト差分
- バックアップ画面の一覧、実行、更新、失敗時導線の配置
- PC 幅と狭い画面幅での優先表示と折り返し方針

### 主要操作の配置

次の操作について、どこに置き、どれを主操作として扱うかを実装前に視覚確認する記録が不足していました。

- ノート作成、保存、編集、キャンセル、削除
- 検索、条件リセット、ページ移動
- タグ追加、タグ削除、既存タグ候補選択
- 復習モードへの切替、本文表示、復習完了
- バックアップ作成、一覧更新、失敗時の再試行

### 状態ごとの表示

normal state 以外の状態を、画面単位でどう見せるかの状態別モックが不足していました。

| 状態 | 不足していた確認 |
| --- | --- |
| loading | 初期取得中、検索中、保存中にどの領域を待機状態にするか |
| empty | ノート 0 件、検索結果 0 件、タグ候補 0 件、バックアップ 0 件の表示 |
| error | API 失敗、保存失敗、バックアップ失敗時の表示位置と再試行導線 |
| validation | 入力項目ごとのエラー位置、表示タイミング、保存ボタンの扱い |
| editing | 編集中であること、未保存変更があることの見え方 |
| saved | 保存完了、削除完了、復習完了の通知方法 |
| review | 本文非表示状態と表示後状態の差分 |

### 空状態・エラー状態

空状態とエラー状態は、テキスト仕様としては扱われていましたが、ユーザーが次に取る行動を視覚的に確認する成果物が不足していました。

- ノートがないときに新規作成へ誘導する表示
- 検索結果がないときに条件変更やリセットへ誘導する表示
- タグ候補がないときに自由入力を許可する見え方
- 保存失敗時に再試行できるのか、入力を継続できるのか
- バックアップ失敗時に何を再試行し、どこでログを確認するのか

### 入力中・保存中・競合時の見え方

入力中、保存中、競合時の UI は、実装前に状態別に確認する記録が不足していました。

- 入力中にプレビューをどう更新するか
- 保存中にボタンを disable するか、二重送信をどう防ぐか
- 保存成功後に閲覧モードへ戻るのか、編集モードに残るのか
- 保存失敗時に入力内容を保持することをどう伝えるか
- 自動保存や楽観ロックを含む Phase 2 UI で、バナーとモーダルをどう使い分けるか
- 409 競合時に再読み込み、後で対応、編集継続をどう提示するか

MVP 実装では自動保存や 409 競合 UI は MVP 外へ整理されましたが、将来 Phase 2 で扱う場合は、正常系だけでなく競合時の画面状態を事前にモック化する必要があります。

## 採用しない案とその理由

採用しない UI 案と理由を残す成果物も不足していました。特に次のような判断は、実装前に明示しておくと後続レビューで判断しやすくなります。

| 不採用案 | 不採用理由 | 再検討条件 |
| --- | --- | --- |
| ノート詳細と編集を完全に別画面へ分ける | MVP では画面数が増え、作成から編集までの導線確認が重くなる | 編集履歴や権限など、詳細と編集を明確に分ける理由が出た場合 |
| Markdown プレビューを保存後だけ表示する | 入力中に表示崩れや checkbox 表示を確認しにくい | 画面が狭く、編集効率が落ちる場合 |
| 空状態を単なる空白にする | 初回利用者が次に何をすればよいか分からない | なし。最低限の誘導文か主操作は必要 |
| 保存失敗を console や小さい文言だけで扱う | 入力内容の安全性や次の行動が伝わりにくい | 非同期保存を持たないごく単純なフォームの場合 |
| 実装後スクリーンショットを設計完了の根拠にする | 作る前の判断過程や不採用案が残らない | 結果確認、README、回帰確認として使う場合 |

## 実装へ渡す UI 決定事項として必要だったもの

実装 task に渡す前に、少なくとも次の UI 決定事項を明文化しておく必要がありました。

- 各画面の主目的と主操作
- レイアウトの大枠と情報優先度
- 主要操作の配置とボタン種別
- normal / loading / empty / error / validation / saving / success の表示
- 編集中、未保存、保存失敗、削除確認、復習完了の表示
- MVP で扱う状態と Phase 2 へ送る状態の境界
- 採用しない案、不採用理由、将来の再検討条件
- 実装後スクリーンショットの用途

## `doc/assets/screenshots/` の扱い

`doc/assets/screenshots/` は実装後確認の記録です。README 掲載、報告、回帰確認、受け入れ材料としては有効です。

ただし、実装前設計の証跡ではありません。スクリーンショットは「作った結果」を示すものであり、「作る前にどのレイアウト案を比較し、どの状態をどう見せると決め、どの案を採用しなかったか」を示すものではありません。

したがって、UI 体験が重要な機能では、実装後スクリーンショットとは別に、実装前のワイヤフレーム、状態別モック、不採用案メモを残す必要があります。

## 今後のレビュー観点

今後 UI 実装 task を切る前には、次を確認します。

- normal state だけで実装に入っていないか。
- 空状態、エラー状態、保存中、競合時の見え方が決まっているか。
- 実装者が主要操作の配置を迷わないか。
- 発注者が採用案と不採用案を見て判断できるか。
- 実装後スクリーンショットを、設計判断ではなく結果確認として扱えているか。
