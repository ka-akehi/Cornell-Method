# MVP Screenshot / Wireframe Layout Review

作成日: 2026-07-08

## 位置づけ

この文書は、実装スクリーンショットと PNG ワイヤフレームのレイアウト差分を整理する設計レビューです。

実装修正 task ではありません。ワイヤフレームを実装へ機械的に合わせるための指示書でもありません。実装結果とワイヤフレーム案を比較し、どちらを今後の採用案に近づけるべきか、または追加判断が必要かを画面ごとに分類します。

## 分類

| 分類 | 意味 |
| --- | --- |
| `wireframe-fix` | 実装や現行 MVP 方針に合わせて、ワイヤフレーム側を修正する候補 |
| `implementation-candidate` | ワイヤフレーム案の方が良い可能性があり、将来実装修正候補にする差分 |
| `needs-decision` | 実装とワイヤフレームのどちらを採用するか仕様確認が必要な差分 |
| `missing-screenshot` | 比較できる実装スクリーンショットが不足している状態 |

## 全体所見

実装スクリーンショットは、余白を広く取り、白いカードを縦に積む現在のアプリ UI としては一貫しています。一方で、PNG ワイヤフレームは、画面全体の情報構造と操作の近接関係を強く示しており、特に新規ノート画面ではワイヤフレーム案の方が「基本情報から Cornell Layout、Summary へ進む」入力体験を短いスクロール量で把握しやすい可能性があります。

したがって、今回の判断は「実装へ合わせてワイヤフレームを直す」だけでは不十分です。MVP の現行実装を正とする差分と、ワイヤフレームを将来 UI 改善候補として残す差分を分けて扱う必要があります。

## 新規ノート NTE-020

新規ノート画面は、今回もっとも設計判断が必要な画面です。実装はフォーム各領域を大きく分けて縦に積み、入力欄を広く取っています。ワイヤフレームは、基本情報を圧縮し、Cue、本文入力、Preview、Summary、保存操作を 1 画面に近い範囲で見渡せる構造です。

特にユーザーが述べた「ワイヤフレームの方がいいレイアウトしている気がする」という感覚は、この画面では妥当な設計論点です。ワイヤフレーム案は、Cornell Method の構造を早い段階で見せ、入力の流れを短くする可能性があります。

| 差分 | スクリーンショット | ワイヤフレーム | 分類 | 判断メモ |
| --- | --- | --- | --- | --- |
| 画面全体の縦長さ | 1750px の長い縦スクロール。基本情報、Cornell ノート、Summary が大きなカードで分離 | 900px 内で主要領域を圧縮して一覧化 | `implementation-candidate` | ワイヤフレーム案の方が全体像を掴みやすい。新規作成時は「何を埋めれば保存できるか」を早く把握できる利点がある。 |
| 基本情報の密度 | タイトル、日付、学習元、概要、タグが広いカード内に大きく配置 | タイトル、概要、日付、学習元タイプ、タグを横並び中心に圧縮 | `implementation-candidate` | 学習元タイトルなど必要項目は維持しつつ、余白と入力幅を圧縮する余地がある。 |
| タグ入力 | 既存タグ select と自由入力を上下 2 段で配置 | タグ名入力、追加、チップを 1 行で配置 | `needs-decision` | 実装は既存候補と新規入力の区別が明確。ワイヤフレームは短く効率的。タグ入力の優先体験を決める必要がある。 |
| Cornell Layout の見え方 | 左 Cue、右本文の 2 カラムは一致。ただし本文 textarea が大きく、preview は下に回る | 左 Cue、右本文内で textarea と preview を横並び | `implementation-candidate` | デスクトップではワイヤフレームの横並び preview の方が Markdown の即時確認に向く可能性が高い。 |
| Cue 追加ボタン | Cue 見出し付近にテキストボタン `Cue 追加` | Cue 見出し右に `+` | `needs-decision` | ワイヤフレームの方が対象領域との近接性は高い。実装のテキストボタンは意味が明確。 |
| Cue 空状態 | `Cue は未追加です。` の空カード | サンプル Cue あり | `wireframe-fix` | normal state を初期作成画面として見るなら、ワイヤフレームも空状態に寄せた方が実装比較しやすい。 |
| Summary | 実装は textarea と preview が縦並びで大きい | Summary 行に入力、preview、次回復習日、保存操作を横並び | `needs-decision` | ワイヤフレームはコンパクトだが、Summary は長文になり得る。実装の広さも合理性がある。 |
| 保存 / キャンセル | 最下部右側。長いスクロール後に到達 | Summary 内の右端に常時近い | `implementation-candidate` | 保存までの距離はワイヤフレーム案が短い。実装を維持する場合は sticky footer などの代替も検討できる。 |
| 見出し文言 | 日本語中心の実画面文言 | 英語見出し `New Note` と設計用タイトル | `wireframe-fix` | 実画面比較用ワイヤフレームとしては、設計 ID と実画面文言を分ける。 |

## Manager 推奨

次に決めるべきことは、ワイヤフレームを実装へ合わせる作業ではなく、画面ごとに採用する情報密度の方針です。

1. 新規ノート画面は、ワイヤフレーム案を将来の UI 改善候補として採用するか決める。
   - Manager 推奨: 採用候補にする。理由は、基本情報、Cue、本文、Preview、Summary、保存操作の全体像が実装より早く見えるため。
2. 詳細閲覧画面は、現行のカード分割を維持するか、Cornell Layout の一体感を優先するか決める。
   - Manager 推奨: 現行実装を当面維持し、概要とメタ情報の圧縮だけを改善候補にする。
3. 一覧画面は、検索フォームの実装密度を正とするか、ワイヤフレームの条件グループ視認性を正とするか決める。
   - Manager 推奨: 実装密度を基本にしつつ、複数件・タグ選択済み・ページャ表示のスクリーンショットを追加して再確認する。
4. バックアップ画面は、実装の軽い説明配置を正とし、一覧だけ列見出しを強めるか決める。
   - Manager 推奨: 説明領域は実装寄せ、一覧の列情報はワイヤフレーム案を改善候補にする。
5. 編集モード、復習モード、モバイルの実装スクリーンショットを追加取得する。
   - Manager 推奨: これらは現時点で採否判断せず、`missing-screenshot` の解消を先に行う。
