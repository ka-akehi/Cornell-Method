# Manager / Worker task を設計する判断基準

作成日: 2026-07-07

このメモは、AI / Worker に作業を依頼するときのタスク分解を学ぶためのメモです。Manager / Worker 運用ルールの正本ではありません。実際の運用は `codex-queue/README.md` と `summary/README.md` を確認します。

## このメモで学ぶこと

- 曖昧な依頼は、成果物と検証が曖昧なまま終わりやすいこと。
- 非 coding task ほど、調査本文をどのファイルに残すかを先に決める必要があること。
- summary は引き継ぎの checkpoint であり、調査本文や設計レビュー本文の代替ではないこと。

## なぜ重要か

AI / Worker は、依頼が曖昧でももっともらしい結果を返せます。そのため、依頼側が目的、対象、対象外、成果物、完了条件を固定しないと、必要な判断材料がファイルとして残らないまま作業が終わります。

タスク設計は、作業者を管理するためだけではありません。何を決め、何を残し、次の人がどこから読めばよいかを設計する行為です。

## 判断の基本

task を切るときは、少なくとも次を分けて考えます。

- 目的: 何を決める、作る、確認するのか。
- 成果物: 完了時にどのファイルや確認結果が残るのか。
- 対象: 読んでよい範囲、変更してよい範囲。
- 対象外: 触らない範囲、判断しない論点。
- 完了条件: 何をもって終わりとするのか。
- 検証: lint、build、リンク確認、記述条件確認など何で確かめるのか。

特に調査、棚卸し、設計レビューは、最終回答だけに結果が残りやすい領域です。本文として残す価値があるなら、先に保存先 Markdown を指定します。

## 初心者が誤解しやすい点

- 「調査してまとめて」と頼めば、必要な場所に成果物が残ると思う。
- summary を成果物本文として扱ってしまう。
- 調査と実装を一つの task にまとめる方が速いと思う。
- 並行できる task と、先行結果が必要な task を同じ扱いにする。
- 「必要なら直す」「いい感じに整理する」のような言葉で対象外が消える。

## 次に同じ判断をするときの見方

作業を依頼する前に、「この task が終わったあと、次の人はどのファイルを読めば判断を再開できるか」を確認します。答えが summary や会話ログだけなら、成果物の置き場が不足しています。

運用ルールや queue の扱いは、このメモではなく `codex-queue/README.md` と `summary/README.md` を正本として確認します。
