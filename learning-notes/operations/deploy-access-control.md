# 外部デプロイとアクセス制御を分けて判断する基準

作成日: 2026-07-07

このメモは、外部デプロイを検討するときの判断基準を学ぶためのメモです。外部デプロイ方針や運用設計の正本ではありません。実装や方針決定では `AGENTS.md`、`doc/`、該当 task を確認します。

## このメモで学ぶこと

- 「デプロイできる」と「本人だけが安全に使える」は別であること。
- URL を共有しないことは、アクセス制御の代わりにならないこと。
- 外部に出す判断では、DB、バックアップ、認証、秘密情報管理も同時に見る必要があること。

## なぜ重要か

個人用の学習ノートでも、タイトル、タグ、本文、復習履歴には個人の関心や行動履歴が含まれます。外部サービスに載せると、公開するつもりがなくても URL、ログ、DB、バックアップの扱いが変わります。

初心者は、無料枠や preview URL の便利さを見て「自分だけが使うから大丈夫」と判断しがちです。しかし安全性は、費用や URL の推測しにくさではなく、誰がどのデータへアクセスできるかで判断します。

## 判断の分け方

外部デプロイを考えるときは、次を一つにまとめない。

- アプリをそのサービスに載せられるか。
- 無料枠で運用できるか。
- production / preview / share URL が生成されるか。
- 認証なしでページや API を開けるか。
- SQLite を継続できるか、外部 DB が必要か。
- 認証情報や DB 接続情報を環境変数で守れるか。
- バックアップと復元の前提がローカル版から変わるか。

この切り分けにより、「デプロイ先を決めたのにデータ保存先が未決」「認証を入れたのに API route が保護されていない」といった抜けを減らせます。

## 初心者が誤解しやすい点

- URL を知っている人だけが開ける状態を、非公開と同じだと思う。
- 無料枠で動くことを、個人情報を置いてよいことと混同する。
- ローカル SQLite と同じバックアップ方針が外部環境でも成り立つと思う。
- 認証は最後に足せばよいと考え、preview URL や API の保護範囲を見落とす。

## 次に同じ判断をするときの見方

まず、外部に出す目的が「学習サイクルの検証」なのか「どこからでも使うため」なのかを分けます。目的が後者なら、デプロイ作業だけでなくアクセス制御、データ保存、バックアップ、秘密情報管理を同じ判断単位にします。

現行仕様の前提は `AGENTS.md` と `doc/` を確認します。このメモの分類や例は、方針決定の正本として使いません。
