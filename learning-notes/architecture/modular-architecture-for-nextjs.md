# Next.js / React で Modular Architecture を主軸にする判断基準

作成日: 2026-07-07

このメモは、Next.js / React アプリで過剰な層分けを避けながら、変更しやすい構造をどう判断するかを学ぶためのメモです。技術設計の正本ではありません。実装方針は `doc/technical/` と該当 task を確認します。

## このメモで学ぶこと

- Clean Architecture / Hexagonal Architecture を名前どおりに持ち込むより、Next.js / React では機能単位の module を主軸にした方が扱いやすい場面があること。
- 層を増やす目的は見た目の整理ではなく、変更理由と副作用境界を追いやすくすること。
- 巨大ファイルを避けることと、過剰分割を避けることは両立して考える必要があること。

## なぜ重要か

保存、削除、復習、PDF、バックアップのような責務が増えると、UI、API、DB、副作用の境界が混ざりやすくなります。一方で、早すぎる層分けはファイル数と判断コストだけを増やします。

設計パターンの名前ではなく、どの変更をどこに閉じ込めたいかを考えることが重要です。

## 判断の基本

Next.js / React アプリでは、まず業務機能単位で module を分けます。層は、module の中で責務が混ざり始めたときだけ追加します。

```text
主軸: 業務機能単位の Modular Architecture
補助: 必要な箇所だけ軽量な層分け
避ける: React UI への Clean Architecture の機械的な適用
```

重要なのは、層の名前をそろえることではありません。変更理由を module 内に閉じ込め、UI、HTTP contract、server 処理、DB / filesystem / PDF などの副作用境界を追いやすくすることです。

## 分ける判断

分割を考えるときは、次の問いを使います。

- 同じ責務が複数箇所に重複しているか。
- 分けることで変更範囲が狭くなるか。
- API contract、DB shape、UI state の混同が減るか。
- 差し替え可能性が現実的にある副作用境界か。
- テストや手動確認の対象が明確になるか。

逆に、wrapper が同名関数を呼ぶだけ、まだ 1 箇所でしか使っていない、名前をそろえること自体が目的になっている場合は分けません。

## 巨大ファイルを避ける見方

過剰設計を避けることは、巨大ファイルを許すことではありません。表示、入力 state、API 呼び出し、payload 変換、validation 表示が 1 component に同居している場合や、Route Handler に request parse、transaction、mapping、error response が詰まっている場合は、責務名で分ける候補になります。

ただし、機能追加とアーキテクチャ移行を同じ task に混ぜると、何が原因で挙動が変わったのか追いにくくなります。境界整理は目的を分けて扱います。

## 初心者が誤解しやすい点

- 有名なアーキテクチャ名を採用すれば設計が良くなると思う。
- UI にも server 側と同じ層名をそろえるべきだと考える。
- 小さい component や endpoint まで先回りして分割する。
- 過剰設計を避けることを、巨大ファイルを許すことと混同する。

## 次に同じ判断をするときの見方

まず「変更対象はどの機能 module に属するか」を見ます。次に、責務が混ざっているのか、重複しているのか、副作用が大きいのか、まだ小さいままでよいのかを分けます。実装方針として固定する場合は、このメモではなく `doc/technical/` 側を更新します。
