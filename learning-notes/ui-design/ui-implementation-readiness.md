# UI 実装前に体験を設計する判断基準

このメモは、UI を実装する前に「画面の見た目」だけでなく「ユーザー体験」をどう設計するかを学ぶためのメモです。Worker へ渡す作業チェックリストや画面仕様の正本ではありません。実装時は `doc/screens/`、`doc/testing/`、該当 task を確認します。

## このメモで学ぶこと

- スクリーンショットは実装後の結果であり、ワイヤフレームは実装前の判断道具であること。
- UI 設計では normal state だけでなく、empty / loading / error / validation / saving / conflict を考える必要があること。
- 採用案だけでなく不採用案を残すと、判断基準を後から学び直せること。

## なぜ重要か

UI は、仕様を画面へ写すだけでは完成しません。ユーザーが迷わず入力できるか、失敗時に戻れるか、保存中や競合時に何が起きているか分かるかまで含めて体験が決まります。

実装後スクリーンショットだけを見ると「画面は存在する」ことは分かります。しかし、作る前にどの配置を選び、どの状態をどう見せると判断したのかは分かりません。設計学習では、この判断過程を残すことが重要です。

## 初心者が誤解しやすい点

- スクリーンショットがあれば UI 設計が完了していると思う。
- normal state の画面だけを描いて、空状態、保存失敗、validation、競合を後回しにする。
- ワイヤフレームを完成デザインや装飾案だと誤解する。
- 不採用案を残すことを無駄だと思う。

## 判断の基本

UI 実装前には、成果物の数ではなく、ユーザー体験の未決事項を確認します。

- どこに何を置くと、次の行動が自然に分かるか。
- 主要操作が画面の目的に対して目立ちすぎたり埋もれたりしていないか。
- 一覧から詳細、新規作成、編集から閲覧、エラー後の再試行などの導線が途切れていないか。
- 入力中、保存中、保存失敗、競合時に、ユーザーが何を待つべきか、何を選べるか。
- validation の表示位置、タイミング、文言が修正行動につながるか。
- 採用案と不採用案から、何を優先した判断だったか説明できるか。

## スクリーンショットとワイヤフレームの違い

- 実装後スクリーンショット: 作った結果の確認。README、報告、回帰確認には有効。
- 画面設計書: 表示項目、入力項目、操作、validation、状態の整理。
- 低忠実度ワイヤフレーム: レイアウト、視線誘導、主要操作の位置、情報優先度の合意。
- 状態別モック: empty / loading / error / saving / conflict などの見え方の確認。
- 不採用案メモ: なぜ別案を選ばなかったかの記録。

ワイヤフレームは完成デザインではありません。色や装飾よりも、ユーザーが次に何をすればよいか、状態変化に気づけるかを確認するための道具です。

## 次に同じ判断をするときの見方

保存、削除、Undo、競合、validation、検索条件、空状態など、ユーザーの判断や復帰導線に関わる変更では normal state だけで判断しません。仕様や画面の正本は `doc/screens/` と該当 task に残し、このメモは判断観点として使います。
