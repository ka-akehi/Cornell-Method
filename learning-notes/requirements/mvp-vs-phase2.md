# MVP / Phase 2 の切り分け基準

作成日: 2026-07-07

このメモは、要望を初回完成ライン、次段階、保留に分ける判断基準を学ぶためのメモです。Cornell Method Notebook の仕様分類の正本ではありません。現行の要件は `AGENTS.md` と `doc/requirements/` を確認します。

## このメモで学ぶこと

- 「価値がある」と「初回完成ラインに必須」は別であること。
- MVP は機能を多く入れることではなく、最初に検証したい目的を成立させる範囲で決めること。
- Phase 2 送りは却下ではなく、検証順序を守るための判断であること。

## なぜ重要か

要望をすべて初回完成ラインに入れると、DB、API、UI、テスト、運用の複雑さが一気に増えます。その結果、本当に確かめたい体験の検証が遅れます。

スコープを分ける力は、作る量を減らすためではありません。何を先に学び、何を後で判断してもよいかを明確にするために重要です。

## 判断の基本

MVP に入れるかどうかは、「便利か」「作れるか」ではなく「これがないと最初に検証したい体験が成立しないか」で見ます。

Phase 2 に送るかどうかは、「価値が低いか」ではなく「初回では簡易版や手作業で代替でき、後から足しても大きく壊れないか」で見ます。

保留にするかどうかは、「将来価値はありそうだが、利用場面、方式、前提技術、運用がまだ決まっていないか」で見ます。

## 初心者が誤解しやすい点

- 価値がある機能は MVP に入れるべきだと思う。
- Phase 2 送りを要望の否定だと捉える。
- 「今作れるか」を優先し、「後から追加すると何が壊れるか」を見落とす。
- 実装量だけを見て、状態管理、エラー処理、テスト、運用の増加を見落とす。

## 判断質問

要望が出たら、すぐに仕様へ入れずに次を確認します。

1. これは何の目的を達成するためか。
2. 中心体験のどこを支えるか。
3. これがないと初回完成ラインは失敗するか。
4. 手作業、簡易 UI、既存機能で一旦代替できるか。
5. 後から追加すると DB / API / UI の前提を大きく壊すか。
6. 状態管理、エラー処理、テスト、運用の複雑さをどれだけ増やすか。
7. 今決める必要があるか、利用後に判断した方がよいか。

## 次に同じ判断をするときの見方

判断理由は、具体的な機能名の一覧ではなく「初回完成ラインの目的」とセットで残します。現在の MVP / Phase 2 分類は変わる可能性があるため、このメモの例を正本として使わず、`AGENTS.md` と `doc/requirements/` を確認します。
