# 設計学習メモ

このドキュメントは、発注者が設計者として成長するために、Manager / Worker が設計判断の理由や判断基準を説明した内容を蓄積するメモです。

今後、発注者から「なぜその判断をしたのか」「判断基準は何か」といった設計学習目的の質問があった場合は、このファイルへ追記します。

## 2026-06-15: MVP と Phase 2 を切り分ける判断基準

### 背景

発注者から、ヒアリング段階で出てきた要望や仕様を、すぐに取り入れるべき要件として整理するのか、Phase 2 以降の要件として整理するのかを判断するポイントについて質問があった。

### 判断の基本

要望を MVP に入れるか Phase 2 に送るかは、**「価値があるか」ではなく「今の完成ラインを成立させるために必要か」**で判断する。

要望は多くの場合、何らかの価値を持つ。そのため「便利そう」「将来使いそう」で MVP に入れると、初回リリースの範囲が膨らみ、主目的の検証が遅れる。

### MVP に入れる判断基準

以下に該当するものは MVP に入れる候補になる。

- その機能がないと、主目的が成立しない。
- 主要ユーザーが初回利用から必ず通る。
- 手作業や簡易運用で代替できない。
- あとから追加するとデータ構造を大きく壊す。
- 受け入れテストの中心シナリオに入る。
- その機能で仮説検証したい。

今回の例では、「本文を隠す復習モード」は MVP に入れる。理由は、コーネルメソッドの「想起」を成立させる中核だから。

### Phase 2 に送る判断基準

以下に該当するものは Phase 2 に送る候補になる。

- あると便利だが、主目的は成立する。
- 利用頻度がまだ不明。
- 手動運用や簡易機能で一旦代替できる。
- 実装、検証、運用コストが高い。
- 依存ライブラリや別プロセスなど構成が重くなる。
- あとから追加しても設計破綻しない。

今回の例では、Rust API、PDF、高機能 Markdown エディタ、D&D は Phase 2 とする。理由は、コーネルメソッドの学習サイクル自体はそれらなしでも成立するため。

### ヒアリング時に使う 5 つの質問

要望が出たら、以下を確認する。

1. これは何の目的を達成するためですか？
2. これがないと初回リリースは失敗ですか？
3. 手作業・簡易機能で一旦代替できますか？
4. 後から追加すると DB / API / UI を壊しますか？
5. この機能の成功をどう確認しますか？

この 5 問で、MVP / Phase 2 / 保留 / 削除候補の分類がしやすくなる。

### 判断の型

```text
主目的に必須 -> MVP
主目的に近いが簡易版で足りる -> MVPでは簡易版、詳細版はPhase 2
便利・拡張・高性能・自動化 -> Phase 2
目的や利用頻度が不明 -> 保留
今の前提と矛盾する -> 削除候補または再ヒアリング
```

### 今回のプロジェクトでの分類例

| 要望 | 判断 | 理由 |
| --- | --- | --- |
| 本文を隠す復習モード | MVP | 想起が成立しないため |
| 復習予定日 / 復習済み | MVP 簡易版 | Review を最低限支えるため |
| 高度な復習タスク画面 | Phase 2 | 一覧フィルタで代替可能 |
| Markdown 専用エディタ | Phase 2 | textarea で代替可能 |
| Rust API | Phase 2 | 小規模 MVP では構成が重い |
| Cue / Tag 差分更新 | Phase 2 | 全置換で代替可能 |
| PDF 出力 | Phase 2 | 学習サイクルには直接不要 |

### 顧客への伝え方

Phase 2 送りは却下ではない。顧客には次のように伝えるとよい。

```text
その要望は価値があります。
ただし初回リリースの目的には必須ではないため、
MVPでは簡易版または代替手段で対応し、
Phase 2の拡張要件として管理します。
```

この伝え方にすると、要望を否定せず、スコープを守れる。

## 2026-06-15: 無料枠での外部デプロイとアクセス制御を分けて判断する

### 背景

発注者から、Vercel にデプロイする場合に自動的に公開URLになるのか、個人利用であれば Basic 認証などを設定すべきかという質問があった。

### 判断の基本

外部デプロイを検討するときは、以下を分けて考える。

- デプロイできるか
- 無料で運用できるか
- URLが生成されるか
- 誰がアクセスできるか
- データをどこに保存するか
- 認証・アクセス制御をどこで行うか

「無料でデプロイできる」ことと「個人だけが安全に使える」ことは別問題。

### 今回の判断

MVP ではローカル利用に留める。

Phase 2 で Vercel に載せる場合は、無料範囲を重視し、Vercel の有料保護機能を前提にせず、まずアプリ側 Basic 認証相当を実装する。

### 判断基準

以下に該当する場合、外部デプロイはアクセス制御とセットで扱う。

- 個人メモ、学習記録、日記、業務メモなど非公開データを扱う。
- URLを知っている人に見られると困る。
- production URL や generated URL が作られるサービスを使う。
- 無料枠の範囲で運用したい。

### 設計上のポイント

- Vercel にデプロイするとアクセス用URLは生成される前提で考える。
- 個人利用目的でも、URL保護がなければ第三者アクセスの可能性を考える。
- 無料範囲を優先するなら、まずアプリ側 Basic 認証相当を検討する。
- 認証情報は環境変数で管理し、リポジトリにコミットしない。
- 認証は MVP には入れず、Vercel deploy とセットの Phase 2 要件にする。

### 顧客への伝え方

```text
Vercelに載せるとアクセス用URLは生成されます。
公開目的でなくても、個人メモを扱うならアクセス制御は必要です。
無料範囲を優先するなら、まずはアプリ側のBasic認証相当をPhase 2で入れるのが現実的です。
```

## 2026-06-21: システム設計で必要な設計書・図と AI 活用時の設計スキル

### 背景

発注者から、システム設計で必要な設計書や図、AI を活用したシステム構築に合わせた設計業務で必要なスキルについて質問があった。

### 判断の基本

設計書や図は、数を増やすことが目的ではない。目的は、実装者、レビュアー、利用者、AI に対して「何を作るか」「なぜそうするか」「どこまで作るか」「どう確認するか」を誤解なく伝えること。

AI を使う場合は、自然文の曖昧な依頼だけでは出力がぶれやすい。そのため、設計者は AI に渡せる粒度まで、目的、制約、入出力、受け入れ条件、対象外を明文化する必要がある。

### 最小構成の設計成果物

小規模から中規模の業務アプリや個人アプリでは、まず以下を揃える。

| 成果物 | 目的 |
| --- | --- |
| 要件定義書 | 何を達成するか、誰が使うか、何を対象外にするかを固定する |
| 画面一覧 / 画面遷移図 | ユーザーがどの画面を通って目的を達成するかを示す |
| 画面設計書 / ワイヤーフレーム | 各画面の入力、表示、操作、エラー状態を整理する |
| 業務フロー / ユースケース | ユーザー操作とシステム処理の流れを確認する |
| ER 図 / データモデル | 保存する情報、関連、制約、削除方針を決める |
| API 仕様書 | フロントエンドとバックエンドの契約を固定する |
| 状態遷移図 | 下書き、保存、削除、復元など状態が変わる処理を整理する |
| 非機能要件 | 性能、セキュリティ、バックアップ、運用、アクセシビリティを明文化する |
| テスト観点 / 受け入れ条件 | 完成判定と回帰確認の基準を作る |

### 図の使い分け

| 図 | 使う場面 |
| --- | --- |
| 画面遷移図 | 画面数や導線を整理したいとき |
| 業務フロー図 | 人の作業とシステム処理を分けたいとき |
| ユースケース図 | 利用者と機能の関係を俯瞰したいとき |
| ER 図 | DB 設計、関連、制約を整理したいとき |
| シーケンス図 | API 呼び出し、保存、競合、通知など時系列処理を確認したいとき |
| 状態遷移図 | draft / saved / deleted / restored など状態管理が重要なとき |
| コンポーネント図 | フロント、API、DB、外部プロセスの責務分担を確認したいとき |
| デプロイ構成図 | 本番、ローカル、DB、バックアップ、環境変数の配置を確認したいとき |

### AI 活用時に特に重要な設計スキル

AI 活用時の設計者には、通常の設計スキルに加えて、AI が迷わない入力を作る力が必要になる。

| スキル | 内容 |
| --- | --- |
| 要件分解力 | 大きな要望を独立した小さな task に分ける |
| 境界設定力 | 対象、対象外、変更してよいファイル、触らない領域を明確にする |
| 受け入れ条件設計 | 完了判定をテスト可能な文にする |
| データモデリング | UI 要望を DB、関連、制約、削除方針に落とす |
| 状態設計 | draft、autosave、conflict、undo、review status などを破綻なく扱う |
| API 契約設計 | request / response / error / status code を固定する |
| 非機能設計 | 性能、セキュリティ、バックアップ、運用、アクセシビリティを設計に入れる |
| レビュー力 | AI の出力を仕様、既存コード、テスト観点に照らして検証する |
| プロンプト設計 | AI に目的、背景、制約、完了条件、検証方法を明確に渡す |
| タスク管理 | 並行できる task と依存する task を分け、1 task 1 file で管理する |

### 判断の型

```text
要望を聞く
-> 目的と成功条件を確認する
-> 画面 / データ / API / 状態 / 非機能に分解する
-> 図で関係や流れを確認する
-> 受け入れ条件に落とす
-> AI / Worker に渡せる小さな task に分ける
-> 実装結果を設計書とテスト観点でレビューする
```

### 重要な注意点

AI を使うほど、設計者の役割は軽くならない。むしろ、曖昧なまま実装へ流すと、AI はもっともらしいが前提の違う成果物を作りやすい。

設計者は「答えを全部自分で書く人」ではなく、「AI や実装者が迷わない問いと制約を作る人」と考えるとよい。
