# 設計学習メモ

このドキュメントは、発注者が設計者として成長するために、Manager / Worker が設計判断の理由や判断基準を説明した内容を蓄積するメモです。

今後、発注者から「なぜその判断をしたのか」「判断基準は何か」といった設計学習目的の質問があった場合は、このファイルへ追記します。

## 2026-06-15: MVP と Phase 2 を切り分ける判断基準

### 背景

発注者から、ヒアリング段階で出てきた要望や仕様を、すぐに取り入れるべき要件として整理するのか、Phase 2 以降の要件として整理するのかを判断するポイントについて質問があった。

### 判断の基本

要望を MVP に入れるか Phase 2 に送るかは、**「価値があるか」ではなく「今の完成ラインを成立させるために必要か」**で判断する。

要望は多くの場合、何らかの価値を持つ。そのため「便利そう」「将来使いそう」で MVP に入れると、初回リリースの範囲が膨らみ、主目的の検証が遅れる。

### MVP に入れる判断基準

以下に該当するものは MVP に入れる候補になる。

- その機能がないと、主目的が成立しない。
- 主要ユーザーが初回利用から必ず通る。
- 手作業や簡易運用で代替できない。
- あとから追加するとデータ構造を大きく壊す。
- 受け入れテストの中心シナリオに入る。
- その機能で仮説検証したい。

今回の例では、「本文を隠す復習モード」は MVP に入れる。理由は、コーネルメソッドの「想起」を成立させる中核だから。

### Phase 2 に送る判断基準

以下に該当するものは Phase 2 に送る候補になる。

- あると便利だが、主目的は成立する。
- 利用頻度がまだ不明。
- 手動運用や簡易機能で一旦代替できる。
- 実装、検証、運用コストが高い。
- 依存ライブラリや別プロセスなど構成が重くなる。
- あとから追加しても設計破綻しない。

今回の例では、Rust API、PDF、高機能 Markdown エディタ、D&D は Phase 2 とする。理由は、コーネルメソッドの学習サイクル自体はそれらなしでも成立するため。

### ヒアリング時に使う 5 つの質問

要望が出たら、以下を確認する。

1. これは何の目的を達成するためですか？
2. これがないと初回リリースは失敗ですか？
3. 手作業・簡易機能で一旦代替できますか？
4. 後から追加すると DB / API / UI を壊しますか？
5. この機能の成功をどう確認しますか？

この 5 問で、MVP / Phase 2 / 保留 / 削除候補の分類がしやすくなる。

### 判断の型

```text
主目的に必須 -> MVP
主目的に近いが簡易版で足りる -> MVPでは簡易版、詳細版はPhase 2
便利・拡張・高性能・自動化 -> Phase 2
目的や利用頻度が不明 -> 保留
今の前提と矛盾する -> 削除候補または再ヒアリング
```

### 今回のプロジェクトでの分類例

| 要望 | 判断 | 理由 |
| --- | --- | --- |
| 本文を隠す復習モード | MVP | 想起が成立しないため |
| 復習予定日 / 復習済み | MVP 簡易版 | Review を最低限支えるため |
| 高度な復習タスク画面 | Phase 2 | 一覧フィルタで代替可能 |
| Markdown 専用エディタ | Phase 2 | textarea で代替可能 |
| Rust API | Phase 2 | 小規模 MVP では構成が重い |
| Cue / Tag 差分更新 | Phase 2 | 全置換で代替可能 |
| PDF 出力 | Phase 2 | 学習サイクルには直接不要 |

### 顧客への伝え方

Phase 2 送りは却下ではない。顧客には次のように伝えるとよい。

```text
その要望は価値があります。
ただし初回リリースの目的には必須ではないため、
MVPでは簡易版または代替手段で対応し、
Phase 2の拡張要件として管理します。
```

この伝え方にすると、要望を否定せず、スコープを守れる。

## 2026-06-15: 無料枠での外部デプロイとアクセス制御を分けて判断する

### 背景

発注者から、Vercel にデプロイする場合に自動的に公開URLになるのか、個人利用であれば Basic 認証などを設定すべきかという質問があった。

### 判断の基本

外部デプロイを検討するときは、以下を分けて考える。

- デプロイできるか
- 無料で運用できるか
- URLが生成されるか
- 誰がアクセスできるか
- データをどこに保存するか
- 認証・アクセス制御をどこで行うか

「無料でデプロイできる」ことと「個人だけが安全に使える」ことは別問題。

### 今回の判断

MVP ではローカル利用に留める。

Phase 2 で Vercel に載せる場合は、無料範囲を重視し、Vercel の有料保護機能を前提にせず、まずアプリ側 Basic 認証相当を実装する。

### 判断基準

以下に該当する場合、外部デプロイはアクセス制御とセットで扱う。

- 個人メモ、学習記録、日記、業務メモなど非公開データを扱う。
- URLを知っている人に見られると困る。
- production URL や generated URL が作られるサービスを使う。
- 無料枠の範囲で運用したい。

### 設計上のポイント

- Vercel にデプロイするとアクセス用URLは生成される前提で考える。
- 個人利用目的でも、URL保護がなければ第三者アクセスの可能性を考える。
- 無料範囲を優先するなら、まずアプリ側 Basic 認証相当を検討する。
- 認証情報は環境変数で管理し、リポジトリにコミットしない。
- 認証は MVP には入れず、Vercel deploy とセットの Phase 2 要件にする。

### 顧客への伝え方

```text
Vercelに載せるとアクセス用URLは生成されます。
公開目的でなくても、個人メモを扱うならアクセス制御は必要です。
無料範囲を優先するなら、まずはアプリ側のBasic認証相当をPhase 2で入れるのが現実的です。
```
