### Update pipeline（backend 実装済み・packaged runtime 未検証）

- 現行コードには GitHub Releases provider、provider-neutral manifest の parsing / normalization / strict validation、compatible selection、公開 direct HTTPS URL 境界、package download、公開鍵署名・SHA-256 検証、archive / bundle validation、atomic な update state、pending update verification / staging revalidation がある。`apply_verified_update` は `Available` かつ `Verified` の candidate に対する引数なしの明示 command だけで起動し、candidate identity、signature・digest、canonical staging path、archive、bundle ID / version / architecture / arm64 Mach-O を再検証して `ApplyPreparation` を atomic に保存し、explicit restart handoff へ渡す。handoff の atomic 永続化が成功した後にだけ exit allowance と restart request を行い、永続化失敗時は restart と exit allowance を行わない。明示 handoff のない persisted `ApplyPreparation` は interruption として扱い、自動 apply / 自動 restart を行わない。
- persisted `ApplyPreparation` と明示 handoff を起点に、pending migration がある場合だけ migration 前 safety backup と DB staging copy を作成し、同じ candidate digest の既存 safety backup は内容と file identity を検証した後にだけ再利用する。複数件が一致する場合は選択・削除せず fail-closed とする。候補 DB の古い順の migration、schema / integrity / foreign key / reopen と、全 application table の read-back を確認してから atomic switch する。`sqlite_*` system table と `_prisma_migrations` だけを除外し、既存 table、column、row の消失・変更を switch 前に検出する。pending migration がない場合も `NO_PENDING` 前に candidate Prisma schema と live / staged SQLite schema の compatibility を検証し、不一致時は backup / switch / cleanup へ進まない。
- staged migration の runner、read-back、switch の failure は typed rollback checkpoint として永続化する。failure が発生した同じ startup で update recovery を実行し、recovery が成功した場合だけ bootstrap へ進む。recovery 自体の failure は fail-closed とし、migration を自動再実行しない。
- apply 直前には、署名済み archive と extracted candidate tree の全 entry を bytes、type、mode、size、追加・欠落、safe internal symlink target まで照合し、不一致を fail-closed にする。archive extraction と recovery は同じ safe internal relative symlink policy を使い、相対 target、bundle root 内、解決先の存在、cycle なし、`MAX_SYMLINK_HOPS` 内だけを許可する。absolute path、backslash、control byte、空 component、`.`、root 外 traversal、dangling link、cycle、hop 超過、special file は拒否する。
- `RestartHealthCheck` の `HealthPending` / `BundleSwitching` / `BundleSwitched` / `CleanupPending` / `RollbackPending` checkpoint は atomic に永続化される。candidate/current の path、bundle identity、version、architecture を検証し、candidate health には packaged app bundle root ではなく固定 runtime root `Contents/Resources/runtime` を渡す。candidate health 成功前は current app / live DB / safety backup を保持し、成功後だけ旧 bundle、staged artifact、不要な safety backup を cleanup する。switch / rollback の copy は safe internal symlink を target string のまま再作成し、cleanup は link 自体を unlink する。
- rollback、SQLite restore、旧 bundle への復帰、不要な staged artifact の cleanup、typed failure は fail-closed に扱う。DB / bundle rollback と restore が成功した場合も、terminal rollback state を記録する前に、対象 failed bundle marker を managed root / safe-tree 検証付きで削除する。marker cleanup に失敗した場合は `RollbackPending` と typed failure を保持する。rollback / restore 成功時は `Available + failure + pending candidate` へ atomic に遷移して `RollbackPending`、phase、recovery を解除し、rollback / restore 失敗時は `RollbackPending` と typed failure を保持する。
- PR #159 の Code Review Issue #164〜#175 は、候補 safety backup の再利用・曖昧性、rollback 後の failed bundle marker cleanup、restart handoff の永続化順序、staged migration failure の同一 startup recovery、全 application table の read-back 比較に加え、次の内容まで実装・static / disposable test・canonical docs に反映している。Issue の自動 close 用文言は PR 本文の責務とする。
